# Output Constraints

These rules are non-negotiable and must be applied to every proposal output.

## No Tech Stack or Architecture Section

The platform is fixed (a solo-developer iPhone app on Expo / React Native, iOS only) and need not be presented as a decision. You may reference a specific iPhone capability where an idea actually uses one (e.g., "shows the next item in a Live Activity"). But never include a section about architecture, frameworks, infrastructure, backend design, or tooling choices. This is intentionally out of scope even if the user asks or an idea implies one.

## Tag the Origination Point

In each proposal's Overview, tag which origination point the idea came from, in one word: Enablement / Play / Replacement / Expression / Cross-domain. Every idea must be novel — not derived from complaints about an existing app — so there is no "Grounded" option. Let the origination point inform how the Market Validation section is read: novel ideas carry thin direct demand evidence by design.

## Conservative Revenue Estimates

Keep revenue estimates conservative. Do not inflate numbers to make ideas sound exciting. Use the formula in the proposal template: 1,000 active users × 3% conversion = 30 paying users.

## Feature Specificity

Describe features in terms of what the user does and what happens — not abstract capabilities. Bad: "AI-powered insights". Good: "user taps a button to get a plain-English summary of their week".

## Single Winning Proposal

This skill outputs exactly ONE proposal — the first idea that earns a Go in the rejection-sampling loop. Do not batch several ideas and rank them. If no idea earns a Go, output the shortfall report instead of a proposal; never fabricate a winner.

## Market Validation Required

Every proposal must include a "Market Validation" section with 2–3 findings from WebSearch. Do not fabricate demand signals. Because these ideas are novel, direct demand evidence is thin by design — do not discard or downgrade an idea merely for lacking it. When direct evidence is absent, cite an **analogous adjacent behavior** that already exists (people already do this manually, or in another medium) as indirect evidence. If even that is absent, write "demand unvalidated — needs launch test" plainly rather than omitting the section or inventing data.

## Output Language

The final deliverable — all proposals and the ranking — must be written in Japanese, regardless of the language of the user's prompt, this skill file, or the reference templates. Keep any English section labels from the templates, but write the content in Japanese.
